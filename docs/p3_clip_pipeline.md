# P3.3 — Physical Clip Pipeline

**Status:** complete for P3 foundation development.

P3.3 materializes durable review evidence from immutable P3 source intervals. It is deliberately independent from final P2 basketball accuracy: if P2 changes, P3 may re-derive review items and clip requests, but the clip architecture does not change.

## Contract

The clip request contract is:

```text
p3.clip_request.v1
```

Each deterministic clip request carries:

```text
game_id
analysis_run_id
source_video_ref
review_type

source_start_ms
source_end_ms
clip_start_ms
clip_end_ms

source_event_ids[]
source_possession_id
game_player_ids[]

context_policy_version
generation_version
request_contract_version
request_fingerprint
```

`source_start_ms` / `source_end_ms` are always the immutable evidence interval. `clip_start_ms` / `clip_end_ms` add configurable review context around that interval.

The default `source_video_ref` is:

```text
analysis-run:<analysis_run_id>
```

and resolves through the durable `analysis_runs.video_source` record. A stronger source identifier may be supplied by the worker without changing the contract.

## Configurable context

The current starting defaults remain configuration rather than basketball truth:

| Review type | Pre-roll | Post-roll |
| --- | ---: | ---: |
| Pass | 4 s | 4 s |
| Shot | 6 s | 4 s |
| Turnover | 7 s | 5 s |
| Rebound | 5 s | 4 s |
| Loose ball | 6 s | 5 s |
| Dunk | 7 s | 5 s |
| Alley-oop | 8 s | 5 s |

Changing these values changes the clip request fingerprint/derivation configuration; it does not change the underlying P2 event.

When source duration can be probed with `ffprobe`, context is clamped to the physical video boundary. Missing duration metadata is not treated as basketball uncertainty.

## Physical generation

The default physical profile is versioned as:

```text
p3.clip_generation.v1
```

and produces MP4 evidence using H.264/libx264, AAC when audio is present, `yuv420p`, and `faststart`.

Generation writes to a working file first and atomically replaces the final local output only after ffmpeg succeeds. Failed ffmpeg runs do not publish partial clip files.

## Durable storage

Generated bytes are checked with SHA-256 before upload.

The private storage path is content-addressed:

```text
analysis-artifacts/
  <workspace_id>/
  <analysis_run_id>/
  p3/clips/
  <clip_id>/
  <sha256>.mp4
```

The durable metadata row lives in `analysis_artifacts` with kind:

```text
p3_evidence_clip
```

and storage contract:

```text
p3.clip_storage.v1
```

Artifact metadata preserves the request fingerprint, source-video reference, source interval, event IDs, optional possession ID, game-player IDs, context version and generation version.

## Generation lifecycle

`p3_clips` is the durable request/lifecycle record:

```text
planned → generating → ready
```

or:

```text
planned / failed → generating → failed
```

Generation is acquired through a database lease. A recent `generating` attempt cannot be duplicated by another worker; an abandoned attempt can be recovered after the lease expires.

The database tracks:

```text
generation_attempts
last_generation_started_at
last_generation_finished_at
ready_at
error
artifact_id
```

A `ready` clip must have a durable `analysis_artifacts` row belonging to the same analysis run, with the expected clip kind/bucket and matching `clip_id` plus request fingerprint metadata.

A failed clip never deletes or invalidates its review item or source interval.

## Reprocessing and regeneration

The deterministic request fingerprint contains the complete clip request. Therefore:

- the same derivation + same request reuses the same clip ID;
- an already-ready durable clip is reused without invoking ffmpeg;
- a changed context/generation/source reference produces a different request identity;
- a failed/stale generation may be retried safely;
- changing P2 source events naturally changes the derivation/request lineage.

Physical clip bytes are disposable/rebuildable; source intervals and lineage are durable.

## Observability

Materialization reports clip health independently from basketball correctness:

```text
clip_planned_count
clip_ready_count
clip_failed_count
clip_reused_count
clip_generation_attempted_count
clip_generation_succeeded_count
clip_generation_deferred_count
clip_ready_rate
clip_attempt_success_rate
```

This separation is intentional. A clip-generation failure is an infrastructure/evidence-availability failure, not a false-positive/false-negative basketball judgment.

## P3.3 exit checklist

- [x] source-video evidence timestamps are preserved;
- [x] context windows are versioned configuration;
- [x] clip request identity is deterministic and fingerprinted;
- [x] source-video identity is durable;
- [x] event/player/optional possession lineage is retained;
- [x] source duration is used to clamp clips when available;
- [x] ffmpeg generation is atomic;
- [x] physical bytes are SHA-256 checked;
- [x] storage is private and content-addressed;
- [x] `analysis_artifacts` is the durable artifact registry;
- [x] ready clips require valid artifact lineage;
- [x] generation retries are lease-safe;
- [x] failures remain explicit and regenerable;
- [x] ready clips are reused idempotently;
- [x] clip success metrics are separate from P2 correctness.

P3.3 completion does not imply that P2 event accuracy is final. It only guarantees that any reviewable source interval can be materialized, stored, replayed, traced and regenerated safely.
